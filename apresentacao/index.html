O QUE É UM SMART CONTRACT?

スマートコントラクト
[DO_PAPEL_AO_CÓDIGO]
UM ACORDO AUTOEXECUTÁVEL

Pense em um contrato comum: você assina um papel. Se a outra pessoa não cumprir o combinado, você precisa contratar um advogado, acionar a justiça e esperar meses ou anos.

[CONTRATO_TRADICIONAL // PAPEL]: "Prometo te entregar o card se você me pagar... (depende de confiança, banco e cartório)"

Um Smart Contract é simplesmente esse acordo transformado em um programa de computador gravado na blockchain:

[SMART_CONTRACT // CÓDIGO_É_LEI]: "SE o usuário escolher o card Y e pagar o valor exato X -> ENTÃO entregue o card Y instantaneamente."

Ele roda 24 horas por dia de forma autônoma e o código nunca muda depois do deploy. O que o dono pode fazer (como pausar a máquina) está escrito no próprio código, aberto para qualquer um conferir.

[O_MODELO_MENTAL]
A MÁQUINA DE VENDAS

A forma mais simples de entender qualquer smart contract no mundo é olhar para uma Vending Machine:

1. ESCOLHA Você aperta o botão do item desejado (ex: Slot A1 = cardId). A máquina trava o slot e indica o preço no display.
2. MOEDA Com o item escolhido, você insere o dinheiro na máquina (msg.value). Nenhum gerente precisa autorizar.
3. REGRA A máquina confere automaticamente: "Tem estoque no slot? O valor é exatamente o preço?" (if … revert).
4. ENTREGA Se o valor for exato e houver estoque: entrega o card instantaneamente. Se faltar estoque ou o valor for incorreto: desfaz tudo e devolve o seu ETH (revert).
[100% AUTÔNOMO] Executa sozinho sem intervenção de nenhum humano.
[REGRAS IMUTÁVEIS] O código e o preço dos cards não mudam após o deploy.
[SEM INTERMEDIÁRIOS] Zero bancos, zero cartórios, transação direta P2P.

// 1. A gaveta de cada Card (cabe em 1 slot de 32 bytes: 30 bytes)
struct Card {
uint128 price; // preço em Wei
uint48 stock; // estoque atual
uint48 initialStock; // tiragem (100)
bool active, exists; // à venda? / cadastrado?
}
// 2. Vitrine e contador
mapping(uint256 => Card) public cards;
uint256 public totalCardTypes;
// 3. Construtor: 5 parâmetros, 30 cards, royalty
constructor(
string baseMetadataURI, string initialContractURI,
uint256 defaultPrice, address royaltyReceiver, uint96 royaltyFeeNumerator
) ERC1155(baseMetadataURI) Ownable(msg.sender) {
totalCardTypes = 30; // A1 até E6
for (id = 1; id <= 30; id++) cards[id] = Card({
price: defaultPrice, stock: 100, initialStock: 100,
active: true, exists: true });
_setDefaultRoyalty(royaltyReceiver, royaltyFeeNumerator);
}
[EXPLICAÇÃO PASSO A PASSO]
1. A struct Card:

Preço, estoque e status de cada card ficam compactados num único slot, o que reduz o gás de cada compra.

2. O mapping cards:

A vitrine: o número do card (1 a 30) devolve os dados do slot.

3. O construtor:

Roda uma única vez, no deploy. Quem faz o deploy vira o dono (Ownable(msg.sender)) e o preço fica igual para os 30 cards.

Dois endereços IPFS:

ipfs://CID/{id}.json descreve cada card; contractURI descreve a coleção.

💡 Estoque individual por card: tiragem de 100 unidades e preço definidos no deploy. [ETAPA_01/05]

// Assinatura: 2 modificadores já protegem a porta de entrada
function buyCard(uint256 cardId, uint256 amount)
public payable whenNotPaused nonReentrant {
// Trava 1 e 2: card existe? quantidade válida?
if (cardId < 1 || cardId > totalCardTypes) revert InvalidCardId(cardId);
if (amount == 0) revert InvalidAmount();
// Trava 3: card ativo? Trava 4: tem estoque?
Card storage card = cards[cardId];
if (!card.active) revert CardNotActive(cardId);
if (card.stock == 0) revert CardIsSoldOut(cardId);
if (card.stock < amount) revert InsufficientStock(…);
// Trava 5: valor EXATO, nem mais, nem menos
uint256 cost = uint256(card.price) * amount;
if (msg.value != cost) revert IncorrectPayment(msg.value, cost);
// … segue para a entrega
}
// Atalho usado pelo jogo: buyCard(cardId) = buyCard(cardId, 1)
[MODIFICADORES & CHECKS]
whenNotPaused:

Máquina em manutenção? Qualquer compra é recusada na hora.

nonReentrant:

Impede que um contrato malicioso compre de novo no meio da própria compra. Testamos esse ataque (slide 17).

revert com erro customizado:

Desfaz tudo e diz o motivo (CardIsSoldOut, IncorrectPayment…). É mais barato que texto e o jogo traduz cada erro para o jogador.

  • Contas: o ETH no contrato é sempre igual ao preço × cards vendidos.
[ACHADO → CORREÇÃO]

A REVISÃO ENCONTROU UM RISCO

ANTES: o dono podia chamar renounceOwnership() sem querer e perder para sempre o saque, a pausa e a gestão.
DEPOIS: a função agora reverte (RenounceDisabled). A posse só muda pelo caminho seguro de 2 etapas.

Limite honesto: testes e análise automática não substituem uma auditoria humana independente. Para uma rede com dinheiro de verdade, ela seria o próximo passo.
